The Speculators Dashboard

How a new model release on HuggingFace becomes a benchmark row on a website — with agents doing the chores and almost no human in the loop.

What it is

A self-updating leaderboard for speculative decoding

  • We publish speculator models — small "draft" models that speed up LLM inference in vLLM.
  • Every model in our HuggingFace collection gets benchmarked on real GPUs: acceptance rate, throughput, speedup vs. the base model.
  • Results land on a public dashboard — a static site, no backend, no database.
  • The whole system is git + GitHub: issues are the queue, a JSON file is the database, pushes are the deploy.
The big picture

Four stages, release to dashboard

1 · Detect
Daily watcher
A GitHub Action scans our HuggingFace collection every day and files one issue per new or updated model.
→
2 · Prepare
Deploy agent
An agent reads each model card and posts a ready-to-run serving command on the issue.
→
3 · Execute
GPU eval
A scheduled runner claims issues, provisions a GPU pod, serves the model, and runs the benchmark.
→
4 · Publish
Static site
The runner commits the results file; the push redeploys the dashboard on GitHub Pages.

The hand-off between every stage is a plain artifact anyone can inspect: a GitHub issue, an issue comment, a JSON file, a git commit.

Component · the website

One static page, one data file

  • Single HTML file on GitHub Pages — no build step, no server, no framework.
  • On load it fetches results.json — the one file the pipeline ever writes.
  • Renders stat cards, per-hardware tabs, filters, a sortable table, and expandable rows (deploy command + detailed metrics per benchmark subset).
  • Charts come from a CDN library; the page works the same locally with make serve.

Because the site only reads one committed file, "the website updated" and "a benchmark finished" are the same event.

Component · the watcher

A GitHub Action files the work

  • Runs daily on a cron (or on demand) in GitHub Actions — this is the only part that lives in CI.
  • Reads the HuggingFace collection, pulls each model's config: algorithm, target model, size, GPU needs.
  • Diffs against results.json — a model whose upstream files changed gets re-evaluated automatically.
  • Files one issue per model: "Eval: <model>", labeled eval:pending — idempotent, never duplicates.
Component · the queue

GitHub issues are the state machine

Queued
eval:pending
Filed by the watcher. Sizing unknown? Also flagged for triage.
→
Claimed
eval:running
A runner picked it up — no double-runs.
→
Closed
eval:done
Metrics committed, summary posted as a comment.
  • Failures become eval:failed with the log tail attached — and get exactly one automatic retry.
  • No queue service, no database. The open-issue list is a live view of the whole pipeline — anyone can see what's running, done, or stuck.
Component · the agents

Agents do the remaining chores

deploy-commands
Reads each pending model's card and the vLLM recipe catalog, then posts a ready-to-run serving command as a comment on its issue — sources included.
run-evals
Works the pending queue on the cluster one model at a time: spins up a GPU pod via devenv, runs the benchmark, tears the pod down, files the result.
run-evals-manual
For when we already have a GPU box: skips the cluster entirely and packs evals across the free GPUs — in parallel.
Same queue, same result
However an eval runs, it ends the same way: metrics written to results.json, committed, pushed, issue closed. Fully interchangeable.

Agents are playbooks a person kicks off — the truly unattended pieces are just the daily watcher and the 30-minute runner.

Component · the runner

Every 30 minutes, one eval, unattended

  • A scheduler on a cluster-connected machine wakes every half hour and claims the next pending issue.
  • Provisions a disposable GPU pod on OpenShift via devenv — right-sized to the model.
  • Inside the pod: vLLM serves the model, the benchmark sweep runs (acceptance length, throughput, latency).
  • Results are normalized into results.json — speedup computed against a stored baseline — then committed and pushed.
  • The pod is always torn down; a sweeper kills anything older than 4 hours.
Two ways to run

Steady-state vs. "we have GPUs now"

Automated — default

  • Unattended, every 30 minutes
  • Cluster pods via devenv
  • One model at a time, safely serialized
  • Retries failures once, then flags for a human

Manual — on demand

  • An agent session you start on a GPU server
  • No cluster needed — uses the local GPUs directly
  • Parallel: several models evaluated at once
  • Ideal for clearing a backlog before a release

Both read from the same issue queue and write through the same path — you can mix them freely.

Why it's built this way

No database, no queue, no backend — git is the database, issues are the queue, and a push is the deploy.

  • Every step is idempotent — safe to retry, safe to re-run, nothing duplicates.
  • State is always visible — the issue list shows the pipeline; git history shows every result change.
  • Compute is disposable — pods exist for one eval, then they're gone.
